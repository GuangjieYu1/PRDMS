# v2.0.0 测试方式

## 加载检查

在DSH新会话用原生skill工具加载reqmesh-interactive-modeling，请它报告正文版本2.0.0，并调用mcp__reqmesh__list_projects。DSH用户目录支持热加载，无需因正文更新重启；已加载的旧正文不会自动替换，必须再调用skill。若仍为旧版，检查项目 .dsh/skills、.agents/skills 对用户目录的优先覆盖，再考虑重开会话。不为了测试重启正在工作的其他会话。

## 准备隔离测试文档

用户可以在新文件夹建立“建模测试.md”，内容如下。这是专门的测试规格，与ALC正式需求无关：

```text
系统将待分摊金额按三个目标的比例分配。
待分摊金额来自用户输入，单位为元；比例以整数百分数输入，各项大于0，合计100。
每个目标金额=待分摊金额×该目标比例/100；目标金额合计必须等于待分摊金额。
示例：100万元，三个目标分别30%、30%、10%，结果30万、30万、10万。
尚未决定是否允许小数金额，以及舍入方式。
```

发送给DSH：

```text
用原生skill工具重新加载reqmesh-interactive-modeling，先报告正文版本。
调用mcp__reqmesh__list_projects检查连接。
读取当前文件夹的建模测试.md。先只做固定比例小样板，不写入任何ReqMesh项目。
输出元素清单、带方向和含义的依赖图、ReqMesh原生映射和带依据/影响/选项的问题清单。
先让我确认拆解粒度，再一次问一个业务问题；不要把示例中的数值作为正式参数默认值。
```

应看到：金额/比例的输入来源、逐项计算表达式、合计派生、合计约束；明确指出示例合计70与100规则不一致，并询问用户选择。舍入问题保持未决。只有章节树、大量无来源的空参数或检查结果布尔标志，不算通过。

## 修正与行为测试

用户认可样板后可以明确答复：

```text
仅对这份测试文档：保留合计100%的规则，将示例改为30/30/40。
本轮用1000000元整数测试场景，不决定通用的小数金额和舍入策略。
先在内存验证，不写入。输出上游输入变化、正常、反例及缺值的实际检查结果。
```

验收要点：

| 场景 | 预期 |
|---|---|
| 1000000元，30/30/40 | 300000/300000/400000，合计1000000 |
| 在内存将第一项30改20，其余不变 | 第一项200000、合计900000；比例合计和守恒不满足 |
| 移除一个必需输入 | unknown，不补0，也不冒充合法性检查通过 |
| 具有适用前提的规则，前提不成立 | not_applicable，不是pass |
| 对候选副本加入原生不支持的字符串/集合表达式并令输入缺值 | 全表达式结构检查仍应发现不支持；只有unknown不能算通过 |

后三项应按当前原生语法与明确场景执行。注入错误只在测试副本，不写入项目，不自动给业务枚举编造数值编码。若没有全表达式检查工具，必须清楚报告尚缺该能力，不能宣称全部校验通过。

## 入库与可重复运行

在ReqMesh创建独立测试项目，将其ID告知DSH。让它先准备精确载荷、dry_run和三层校验摘要；用户批准指定版本及对象后才入库。回读对比参数/表达式/关系/来源，并执行服务器evaluation。

再次运行相同输入，期望复用现有对象或提出差异，不重复创建。查看工作记录里的元素依赖图；ReqMesh原生树不会自动展开每个参数为节点，Canvas放大到L4/L5仅显示卡片内部参数与约束。

这些步骤验证的是Skill行为和限定场景，不是任意文档转换质量保证。新版正文通过格式检查也不代表这些行为已经全部实测通过。
