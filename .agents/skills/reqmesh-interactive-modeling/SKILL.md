# ReqMesh 交互式建模

版本：2.1.0（固定产物目录 + 探索隔离）。首次加载或被要求核实版本时报告此版本；不能仅凭旧对话或目录描述声称已加载新版。

完成“转换 → 发现问题 → 与用户确认 → 修正模型 → 验证 → 批准入库 → 回读核对”。以 ReqMesh 原生表达能力为边界，不另建本体平台，不按文档章节机械建节点，不将业务对象一律当作软件组件。

## 开始前

确定输入材料和目标项目；已明确的信息沿用，不重复询问。读取原文并保留版本标识及可定位的段落/行号；原文不因建模而改写。

两项**必须在开工时一次说清**，不留给中途补：

1. **产出目录**：按"工作产物"一节建 `reqmesh_validation/<需求简述>-<YYYYMMDDHHmmss>/` 与四件套骨架。
2. **暂存项目与目标项目**：需要写入才能检查时，写进哪个**暂存项目**；确认结果写进哪个**目标项目**。工具集没有建项目能力，缺暂存项目时请用户先建。见"作废、撤销与探索隔离"。

发现当前可调用的 ReqMesh MCP 工具并检查参数 schema、权限与服务版本。读取目标项目的相关需求、组件、定义、关系和校验结果，处理分页；记录读取范围，不能将局部搜索无结果称为全项目无冲突。身份不明或连接失败时可以继续本地草拟，不臆造项目或远端数据。

首次执行或工具能力变化时读 [references/native-capabilities.md](references/native-capabilities.md)。该文件是已核实版本的能力提示，实时 schema 优先。

## 先做小样板，再扩展

首次建模先选择一个能体现输入、计算和约束的代表性片段；没有计算的需求则选择有明确主体、前提和结果的片段。先交付该片段的元素表、依赖图、原生映射及问题，再请用户判断拆解粒度和含义。用户已认可的样板直接沿用；未认可时不批量铺开整份文档，不以节点数量作为进度目标。

样板选择是执行选择，不是业务裁决。样板中正式未知值与独立测试场景分开；不能把三项示例的通过推广为任意项数的业务规则。用户要求仅分析时，不创建远端草稿。

## 元素与依赖：必交付的建模候选

在写入前维护可检查的元素表，每项至少包含：稳定候选标识、含义/角色、原文版本与位置、所属对象、原生字段路径、输入来源或计算表达式、依赖、事实/义务/示例/假设/决定分类、未决问题。字段缺失显式标明未知，不补造内容。

角色包括需求义务、系统组成、外部输入量、派生量、约束和关系。它们是建模检查角色，不是新增的ReqMesh实体类型。参数可用“对象ID＋参数名”定位；约束在本地工作记录中有稳定引用并绑定候选版本及原生字段位置，不能给原生API发送未支持的ID字段。

- 外部输入量说明来自用户配置、接口、测量还是其他已知来源，并注明单位及取值要求。来源未说明属于信息缺口。
- 派生量必须给出依赖和原生可执行表达式；无法表达时标为待建模/表达限制，不把它改称运行期输入来完成任务。例如明细合计必须追溯到明细；有证据表明外部系统负责计算时才按外部输入处理。
- `name_unique == 1`、`ratios_are_integers == 1` 等判断标志只能作为外部判定输入，不能冒充它们所指的完整业务规则。必须说明检查者、检查范围与判定依据；尚不明确就提出问题。
- 约束说明作用对象、前提、所依赖的值及违反含义。无依据的前提编码、阈值、容差或默认值均不能擅自增加。
- 列出每条实际依赖，区分层级、计算引用、约束引用和追踪关系，不能都压成parent，也不能把追踪边当成计算引用。

同时输出两种视图：需求/组件层级候选，以及元素依赖图。默认使用可随工作记录保存的 Mermaid 图；节点引用元素表标识，边来自明确表达式/绑定/关系，推测边必须标为待确认。无跨对象计算依据时不要为“看起来连通”发明连接。

当前ReqMesh Canvas能在卡片内展示参数/约束，但不会自动把所有参数展开为独立节点及依赖线。没有专用视图时交付Markdown/Mermaid候选图并说明这是工作产物，不能宣称已新增ReqMesh内置图功能。用户查看UI时说明当前缩放与折叠状态。

## 工作产物：固定目录与固定四件套

产物**不是随手放的**。每次建模一律在下列位置、按下列命名与结构产出，不得改动形状：

```
reqmesh_validation/                          ← 当前工作目录（cwd）下的固定目录，只建一次
└── <需求简述>-<YYYYMMDDHHmmss>/             ← 每次建模一个，时间取开工时刻（本地时区）
    ├── 01-候选模型.md
    ├── 02-问题清单.md
    ├── 03-决策记录.md
    └── 04-变更与验证报告.md
    附件/                                    ← 可选：写入 payload、原始工具回执
```

命名规则：

- `<需求简述>` 取自需求文档名或主题，**只保留中英文、数字与连字符，不含空格与斜杠，长度 ≤ 20 字**。
- `<YYYYMMDDHHmmss>` 为开工时刻的 14 位数字，**必须是目录名的最后一段**。
- 例：`reqmesh_validation/成本分摊方案-20261010023045/`

四份文件的内容边界（固定：不得合并、改名或省略）：

| 文件 | 必含 |
|---|---|
| `01-候选模型.md` | 元素表（标识 / 含义 / 原文位置 / 原生字段 / 输入或表达式 / 依赖 / 分类）、依赖图（Mermaid）、原生映射与表达缺口 |
| `02-问题清单.md` | 每条含 ID、类别（阻塞建模 / 疑似冲突 / 可选建议）、原文位置与短引文、影响对象、可选处理与后果、推荐项 |
| `03-决策记录.md` | 用户原话与决定、适用范围、被否决选项、**暂存项目与目标项目的区分**、批准范围与回执索引 |
| `04-变更与验证报告.md` | 变更包、校验分层结果（结构 / 完整性 / 场景）、写入清单与回读差异、剩余问题 |

执行约定：

- **开工即建目录与四个文件骨架**；内容未产生时写"待补"，本次不涉及时写"本次未涉及"，保证形状稳定。
- 目录已存在时**不覆盖**，另开一个时间戳目录。
- 顶层固定四个文件；payload、工具回执等一律放 `附件/`，不新增第五个顶层文件。
- 没有可写工作区时，在对话中保留同样四段结构，并显式说明未落盘。
- 产物是可续接的工作记录，**不是另一套权威本体数据库**；权威数据在 ReqMesh。

## 建模与发现问题

从原文提取原子义务、数量、计算、适用条件、关系和场景；区分规范、事实、示例、假设和用户决定。每项候选保留原文依据以及映射理由。

优先复用已有原生对象、参数和定义。名称相同不足以确认同一对象；识别不确定时提出问题。保留既有 ID、未涉及字段与关系；删除、合并和替换都属于明确变更。

数值写入 parameters，计算使用支持的 expr，条件约束保留 assume，关系遵循该项目已有语义。纯描述文本不能冒充可执行约束。确定性的格式/单位转换可执行并记录等价依据；缺失单位、舍入策略、默认值、适用范围以及可能改变行为的解释须由用户决定。未知数值不补为 0。

逐项识别：信息缺失、映射不确定、原生表达能力不足、新旧需求疑似冲突。比较冲突时检查主体、时间、范围、单位与前置条件，区分已证实矛盾、特定场景失败和待确认歧义。列出直接受影响对象和可追踪依赖；无法确定的影响范围显式标记。

反例依赖尚未选择的映射时，结论必须带该假设。例如“若把界面百分数直接用于小数比例公式则放大100倍”是条件性反例，不是已证实的现行业务矛盾。表达能力缺口先核查组合方式、原生引用及 rollup 等聚合能力；区分单字段限制、当前 MCP 缺工具、尚未验证的替代映射与原生能力确实不足。

正式规则中的未知参数保留未知；演示用定值放在明确标识的场景候选中，不把固定三项示例当作任意项数的通用规则。改变表示方式时保留业务不变量：如整数百分数改用小数表示，原有百分数粒度不能无声丢弃。检查通过只适用于实际运行的候选版本和场景，不保证所有业务输入正确。

跨对象计算引用不能用参数副本或仅追踪关系替代；这种改变会失去随源参数更新的行为。新 ID 同时满足项目命名与表达式引用语法；既有 ID 不因表达式限制而擅自改名。无法保持引用时提出准确的映射问题，验证依赖源参数改变后派生结果确实随之变化。

维护一份可续接的工作记录：源版本、目标项目、已读对象指纹、候选变更版本、问题、用户原话及决定、检查结果、批准范围和执行回执。只保存本任务需要的材料，不存凭据。没有可写工作区时在对话中保留结构化记录。

## 交付措辞：说人话

面向用户的回复以**结论与影响**开头，依据放在后面。具体要求：

- 用业务语言说清"哪里有问题、为什么算问题、会带来什么后果、可以怎么处理"，不堆"元素 / 依赖 / 原生映射 / AST"这类内部术语；必须引用原生字段时，同时给出它对应的业务含义。
- 表格只用于必须逐项对照的场景（元素表、问题对照）；叙述性结论用句子讲，不拿表格代替解释。
- 过程性动作（读了什么、跑了什么命令）不作为交付内容；一段话之内先给结论。
- 四份产物已在磁盘上时，回复只给**路径 + 一句话概括**，不把文件内容整段复述到对话里。
- 用户表示看不懂，说明没讲清；换说法重述，不要原样重复。

## 与用户确认

每个需要裁决的问题包含：

- 问题 ID、类别和具体不确定点。
- 原文位置与必要短引文；涉及旧需求时附其 ID、当前内容和版本依据。
- 会影响的对象、规则、计算或下游依赖，以及尚未查明的范围。
- 可选处理方式及各自后果；推荐项标明为建议，包含保留未决的方式。

加入一个能区分不同解释的具体场景。将“阻塞建模的问题”“待核实的疑似冲突”“可选设计反思建议”分开；建议不能冒充原文缺陷或自动成为写入内容。默认一次讨论一个问题，除非用户要求分组；可先提供完整问题清单以供浏览。

按依赖先问能回答的问题，遵守用户偏好的一次一问或分组方式。等待期间可继续独立分析，但不执行依赖未决答案的业务变化。用户沉默、模型置信度高、工具白名单或“继续分析”均不构成业务裁决。

用户回答后记录其适用范围，更新候选并重查受影响部分。教学假设和正式需求决定分开；建议不因被重复描述而升级为决定。含糊答复不能用于批准多个不相容选项。

表达能力不足时说明准确缺口，可建议保留为明确未执行的描述、调整建模方式或补充工具能力；须由用户选择，不能静默降级或绕过 MCP 写底层文件。

## 验证与批准

检查候选 schema、引用、表达式名称与单位、约束前提、对象关系和新旧差异。能使用 ReqMesh 相同版本的原生校验器进行候选离线求值时优先使用；隔离环境必须明确，不能为试验先写正式项目。

验证分三层，分别报告覆盖与缺口：

1. **结构与表达式检查**：无论参数是否有值、前提是否成立，都遍历所有expr、assume及已引用Definition的表达式，检查完整语法、原生支持的运算/常量/函数、参数引用存在性、名称与循环依赖。AST可解析不等于原生可执行。不能依靠求值器的首次unknown、条件短路或not_applicable跳过剩余表达式。缺少确定性检查工具时记录“结构检查未完成”，可在授权工作区用当前原生语法实现并运行检查，但不能声称现有MCP已提供该能力。
2. **建模完整性检查**：外部输入有来源、派生量有依赖、前提与粒度保留、关系端点清楚、没有用参数副本或外部布尔标志代替未建模的推导。逐项证据不足的地方回到问题清单。
3. **场景行为检查**：对当前片段运行正常场景、违反约束的反例、缺值、前提不成立（存在前提时）和上游变化测试。场景值明确为测试输入，不写成正式默认值。跨对象源值变化必须使派生结果按表达式变化；不能用只有一个定值的pass证明依赖已成立。

特别注意：`alc_type == 'D'` 在alc_type缺值时可能先返回unknown，有值后才暴露不支持字符串的错误。这个unknown不代表表达式合法。需求级verdict数量和逐条约束数量分别统计；可执行、尚未校验、已批准描述降级、未建模分别计数。error=0、追踪覆盖率100%不构成完成判据。

分别报告语法/结构有效、求值通过、违反约束、未知、不支持和检查执行错误；不以覆盖率、成功 HTTP 响应或语言模型意见替代语义验证。服务端项目报告通常只覆盖已落库数据，不能证明未写候选有效。

保留原生 not_applicable（前提不成立）状态，不能归入通过。校验结论注明候选版本/摘要、场景和覆盖范围；抽象占位 ID 上测试通过不意味着最终写入 ID、引用或 payload 已通过，写前必须核对最终载荷。没有校验器时不能用自然语言推理声称语义校验通过；有校验器也不能称其保证业务语义正确。

可调用 dry_run 时显式设置 true；预览失败不改为真实写入。缺少候选执行校验能力时，说明已验证和未验证部分，保持待校验状态；不得宣称已完成验证。若用户明确选择记录不可执行的描述，仅按该降级范围准备写入，不标为通过。

在任何真实写操作前展示具体变更包：项目、候选版本、新增/修改/删除对象及字段差异、来源和裁决、校验结果、未决或降级部分、调用顺序以及失败后的可恢复边界。得到用户对该包的明确写入批准后才执行；已存在且覆盖同一包的批准直接沿用。业务选择和写入批准可以在同一明确答复中给出，但不能相互推定。

受未决业务解释影响的变更保持待裁决。可独立且验证完成的子集，仅在用户批准该明确子集后写入；不能声称整份需求已经完成。

## 作废、撤销与探索隔离

**作废（deprecated）是业务裁决，不是撤销手段。** 它表示"该需求不再有效"，会永久留在项目里，并进入覆盖率、求值、报告和后续建模的视野。**不得**用逐条作废来撤销未获批准、已被推翻或纯属试验的建模——那不是撤销，是把垃圾留在模型里。

需要"先写进项目才能查"时（例如结构检查依赖项目 id），按下列隔离：

1. **探索写入进暂存项目**，目标项目只接收已批准的变更包。开工时与用户确认哪个项目是**暂存项目**、哪个是**目标项目**，并记入 `03-决策记录.md`。
2. 暂存项目**不追求整洁**：可以累积、可以整项目废弃。它的存在不污染目标项目。
3. 当前工具集**没有建项目 / 删项目能力**。没有可用暂存项目时，请用户在 Web UI 新建一个（或整项目删除），**不得**把试验写进目标项目。
4. 若已误写入目标项目：**如实报告，不要用逐条作废掩盖**。请用户在项目层处理（删除整个项目重建，或明确接受这些记录），并说明残留会影响覆盖率与后续判断。
5. 用户只说"继续分析"、沉默或提高模型置信度，均不构成写入授权；探索写入同样要求暂存项目存在且用户知情。

## 受控写入与回读

写入前重新读取受影响对象及必要依赖，核对基础状态。发现并发变化时重算差异；实质变化使原批准失效。没有版本条件写入能力时说明检查与提交之间仍有竞态，不能保证原子提交。

使用当前已批准的 MCP 写工具，显式设置 dry_run=false，并遵守工具审批门。先创建依赖目标，再建立引用；有循环依赖时仅在原生模型允许且变更包已描述的情况下分步写入。更新集合字段时确认是替换还是合并，防止清空未涉及内容；未提供与显式 null 不混用。

每个成功操作保存回执并回读核对关键字段：ID、类型、参数值/单位/表达式、约束/前提/绑定、关系、来源。遇到超时或不确定结果先回读，再决定是否重试；不盲目重复 create。部分成功时停止依赖写入，列出已完成、失败和未执行项。恢复不得越过原批准范围，回滚不默认安全或已授权。

全部操作后重新读取相关对象和关系，运行可用的项目 validation/evaluation，并区分原有问题与本次新增问题。返回实际写入清单、回读差异、检查覆盖和剩余问题。读取失败或内容不一致时标为“写入已返回，核对未完成”，不能报告成功闭环。

完成本 Skill 不意味着产品实现通过验证，不自动运行或伪造产品测试，不自动评审通过或冻结基线；这些仅在用户明确要求且工具支持时另外执行。

## 完成判据与自测

完成范围必须明确到片段/对象：用户认可拆解粒度；元素能追溯来源；输入—派生量—约束的依赖可解释且适用的场景测试已执行；未决问题和表达缺口显式保留；批准载荷与回读一致。只有候选或测试未完成时分别报告，不用“全部完成”掩盖这些差异。

用户询问如何验收或要求自测时，读取 [references/testing.md](references/testing.md)。该参考中的数值仅用于隔离测试，不作为真实业务裁决。
